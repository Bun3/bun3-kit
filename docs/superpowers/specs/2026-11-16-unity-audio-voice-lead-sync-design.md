# Unity Audio 음성 앞서 쓰기와 Dissonance 동기화 정렬 설계

- 상태: 구현 (2026-11-16), 사용자 결정 K "bun3-kit에서 기계음 근본 수정 시작"
- 적용 패키지: `com.bun3.unity.audio.dissonance.steamaudio` 0.4.2 → 0.5.0
- 선행 설계: [네이티브 스페이셜라이저 출력](2026-11-12-unity-audio-native-spatializer-output-design.md) (메인 스레드 링 쓰기)
- 첫 적용 게임: 쥬라기 낙원(JP)

## 의도

0.4.0부터 음성은 메인 스레드가 링 클립에 앞서 쓴다(오디오 스레드에서 C#을 없애기 위한 결정, 유지). 그 뒤 메인 스레드가 수백 ms 멈추면 음성이 비고, 이어서 몇 초 동안 음높이가 올라가 기계음처럼 들렸다. 이번 작업은 메인 스레드 정지가 있어도 음높이가 흔들리지 않게 하고, 짧은 정지는 공백 없이 넘기게 한다.

## 원인

Dissonance `SynchronizerSampleSource`는 첫 `Read` 시점부터 흐른 실제 시간과 읽은 샘플 수를 비교한다(`DesyncCalculator`). 차이가 29 ms를 넘으면 차이 1초당 15% 비율로 재생 속도를 바꾸고, `Resampler`는 1%를 넘는 속도 변화부터 실제로 리샘플한다(음높이 변화).

- 앞서 쓰기: 첫 쓰기에서 리드만큼 한 번에 읽으므로 Dissonance에는 항상 리드만큼 "앞서 감"으로 보인다. 0.06초는 1% 미만이라 들리지 않지만, 리드를 0.2초로 늘리면 2.3% 느려진다(측정).
- 정지: 링이 바닥나면 기존 코드는 놓친 구간을 건너뛰고 그 음성을 나중에 이어 읽었다. Dissonance에는 정지 시간만큼 "뒤처짐"으로 보여 재생을 빠르게 하고, 그동안 지터 버퍼를 빨리 소모한다.

JP 측정(수정 전 0.4.2, 리드 0.06초, 수신 가상 플레이어에 `Thread.Sleep` 주입, 6초 관찰):

| 정지 | 대기실 최대 속도 변화 / 1% 초과 시간 | 인게임 최대 속도 변화 / 1% 초과 시간 |
|---|---|---|
| 100 ms | 0.37% / 0초 | 0.35% / 0초 |
| 200 ms | 2.2% / 5.4초 | 1.2% / 1.3초 |
| 300 ms | 4.6% / 6.0초 | 4.7% / 6.0초 |
| 400 ms | 6.9% / 6.0초 | 7.4% / 6.0초 |

원격 발화자가 말을 시작할 때마다 렌더러를 새로 만든다는 가설은 확인되지 않았다. 자연 종료된 발화는 렌더러·HRTF·효과를 재사용한다(JP에서 발화 4회 동안 같은 리소스 객체, 기존 테스트 `NaturalSpeechRestartReusesNativeRendererAndDriver`). 재생성은 리셋·플레이어 변경·장치 변경 때만 일어난다.

## 결정

1. **시계 먼저 시작, 리드 뒤 재생**: 새 발화 세대를 만들 때 빈 `Read`로 Dissonance 시계를 시작하고, 리드만큼 시간이 지난 뒤 첫 쓰기와 `AudioSource.Play`를 한다. 앞서 쓴 리드가 시계와 맞아 리드를 늘려도 속도가 바뀌지 않는다. 대가로 음성 전체가 리드만큼 늦다. 0.4는 첫 쓰기에서 리드를 지터 버퍼에서 한 번에 꺼내 총 지연은 그대로였지만, 그만큼 네트워크 지터 여유가 줄었다(Dissonance 최소 지연 60 ms에 리드 60 ms면 여유가 거의 없다). 0.5는 지터 버퍼를 그대로 두고 지연을 리드만큼 더한다. JP `MeetingVoiceIntegrationTests`의 채널 전환 직후 무음 확인은 이 지연만큼 대기를 0.2→0.35초로 늘렸다.
2. **정지 구간은 건너뛰어 소비**: 언더런 때 재생 위치가 지나간 음성을 읽어서 버린다(`VoiceClipRing.SkipFrames`). 시계와 읽은 양이 같게 유지되어 속도 보정이 없다. 정지 동안의 음성은 잃는다(어차피 무음으로 재생된 구간). 시작·장치 재설정 재개가 30 ms 넘게 늦으면 같은 방식으로 늦은 만큼 건너뛴다. 30 ms 이하는 Dissonance 허용 오차(29 ms)와 리샘플 기준(1%) 안이라 첫 음절을 지키려고 건너뛰지 않는다.
3. **기본 리드 0.06 → 0.1초**: 약 100 ms까지의 정지는 공백 없이 재생한다. 늘린 만큼 음성 지연이 늘어난다. 게임이 `LeadSeconds`로 바꿀 수 있다.
4. **진단**: `TotalUnderruns`, `SkippedSeconds`, `PlaybackRate`(Dissonance 동기화 속도), `LogUnderruns`(언더런마다 경고 로그).

## 검토한 대안

| 대안 | 판단 |
|---|---|
| 리드만 늘림 | 기각. 시계와 어긋나 리드 0.2초에서 2.3% 느려진다(테스트 음성 대조로 확인). |
| 오디오 스레드·`PCMReaderCallback`에서 채움 | 기각. 선행 설계의 제약(오디오 스레드에서 C# 금지, GC가 믹서 전체를 멈춤)과 충돌한다. |
| 백그라운드 스레드에서 디코딩 | 보류. `AudioClip.SetData`는 메인 스레드 전용이라 쓰기는 여전히 메인 스레드가 해야 하고, 디코딩만 옮겨서는 정지 중 공백이 남는다. |
| Dissonance 동기화 끄기 | 기각. 동기화가 내부 타입이고 SDK를 수정하지 않는다. 네트워크 지터 보정도 함께 잃는다. |
| 정지 뒤 음성을 늦게라도 이어 재생 | 기각. Dissonance가 지연을 따라잡으려 속도를 올린다(현재 증상). |

## 한계

- 리드보다 긴 메인 스레드 정지(GC 수백 ms, 씬 로드)는 여전히 그 길이만큼 음성이 빈다. 음높이는 바뀌지 않는다. 공백을 없애려면 리드를 정지 길이만큼 늘려야 하고, 그만큼 지연이 커진다.
- 4초(링 길이)를 넘는 정지는 재생 위치 진행을 링 한 바퀴 이내로만 알 수 있다(기존과 같음).

## 검증

- `VoiceClipRingTests`: 언더런 건너뛰기 양, 늦은 시작, 건너뛴 음성의 전달 집계.
- `DissonanceSteamAudioPlaybackTests.MainThreadStallSkipsSpeechWithoutChangingPlaybackSpeed`: 리드 0.2초, 실시간 패킷, 400 ms 정지. 수정 코드를 끈 대조 실행에서 정지 전 속도 변화 2.3%로 실패, 수정 후 정지 전후 0%, 언더런 1회, 0.21초 건너뜀, 이후 무음 블록 0.
- JP MPPM 측정(0.5.0, 리드 0.1초, 위와 같은 정지 주입): 대기실·인게임 모두 정지 100~400 ms 각각 언더런 1회, 최대 속도 변화 0.1% 이하, 1% 초과 시간 0초. 대기실 건너뜀 10/110/220/300 ms.
- JP `FreeformVoicePlaybackTests`, `MeetingVoiceIntegrationTests`(대기 조정 후) 3회 통과.
