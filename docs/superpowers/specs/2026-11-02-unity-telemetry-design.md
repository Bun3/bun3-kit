# Unity 텔레메트리 패키지 설계

> 상태: 설계 초안(2026-11-02). 첫 사용처는 쥬라기 낙원(JP)이며, JP의 분석 브랜치 `✨/analytics-log-system`에서 함께 전환한다.

## 1. 의도

bun3 Unity 게임은 타이틀·로비·인게임 화면에서 플레이어가 한 행동과 그 결과를 기록한다. 기록 하나를 남기면 로컬 파일, 분석 서버(PostHog), 오류 추적(Sentry), 에디터 콘솔에 함께 들어간다.

JP는 이 수집 장치를 게임 코드(`unity/Assets/_Game/Scripts/Telemetry/`, 약 38개 파일)로 먼저 만들었다. 그중 게임 지식이 없는 부분을 bun3-kit 패키지로 내려, 다음 게임은 이벤트 정의와 게임 고유 값만 작성하게 한다. 근거는 이 저장소의 제1 원칙이다. "두 번째 게임에서도 똑같이 짜게 될 코드라면 프레임워크 몫이다."

## 2. 사용자 결정 (원문 인용)

   - Claude 질문: "다음 게임이나 bun3 서버에서 이 텔레메트리를 쓰게 되는 장면을 떠올리면, 어디서 무엇을 기록하고 싶으세요?"
   - 원문: "뭐 그때도 각 타이틀/로비/인게임 등등에서 유저 행동이나 행동에 의한 결과를 기록할 것 같아"
2. **서버 분석은 나중에 정한다.** 서버 `Bun3.Server.Core.ActionLog`와의 관계를 물었다.
   - 원문: "서버쪽 bun3-kit 코드에도 이미 비슷하게 actionlog 같은게 있는데, 이걸 나눠야지 할지 어떻게 분리해야 할지는 잘 모르겠네."

   - 서버 이벤트를 분석 도구로 보낼지 묻자. 원문: "그건 나중에 생각하자"
3. **공통 속성과 플레이어 ID.**
   - Claude 제안: kit의 고정 공통 속성은 어느 게임에나 있는 값(플레이어 ID, 실행 ID, 빌드, 환경, 씬, 언어)만 둔다. `lobby_id`·`match_id`·역할 같은 값은 게임이 덧붙인다. kit은 Steam을 모르고, SteamID는 게임이 플레이어 ID로 넣는다.
   - 원문: "공통속성은 확인. 플레이어 ID도 확인"

## 3. 목표 · 비목표 · 안티목표

**목표**
- 게임 지식이 없는 수집 장치를 Unity 패키지로 제공한다. 진입점, 허브, 기록 형식, 저장소, 자동 기록, 환경 옵션, 속성 거르기가 해당한다.
- JP가 같은 분석 브랜치에서 kit 패키지로 갈아타고, 옮긴 사본을 지운다. JP에는 이벤트 정의와 게임 고유 값만 남는다.

**비목표**
- 서버 분석과 서버 `ActionLog` 변경(결정 2).
- 채팅 본문·인증 토큰을 제외한 가리기 기능(결정 4). JP의 참가 코드 가리기(`JoinCodeMask`)와 닉네임 차단은 kit으로 옮기지 않고 없앤다.
- JP 기존 기록 형식과의 호환(결정 6).
- 미션 팝업의 "중단" 판정(`MissionPopupTracker`)과 플레이어 번호(`PlayerNumbers`)의 일반화. 둘 다 JP에 남는다. 두 번째 게임에서 필요해지면 그때 내린다(§7-5).

**안티목표**
- kit이 로비·매치·역할·방 같은 게임 개념을 아는 것.
- 분류나 저장소를 켜고 끄는 스위치를 두는 것(앞선 결정).
- 입력칸 내용, 채팅 본문, 인증 토큰이 어느 저장소에든 들어가는 것.

## 4. 구조

### 4.1 패키지

| 패키지 | 내용 | 의존 |
|---|---|---|
| `com.bun3.unity.telemetry` | 진입점, 허브·빌더, 기록 형식, 환경 옵션, 속성 거르기, 저장소(로컬 JSONL·콘솔·기록 보관), 자동 기록(UI 조작·씬 전환·엔진 로그) | UniTask, ZString |
| ↳ 팝업 연동 어셈블리 | `com.bun3.unity.ui`의 `PopupStack.Opened`/`Closed`를 듣는 팝업 기록. UI 패키지가 있을 때만 컴파일된다 | `com.bun3.unity.ui` |
| `com.bun3.unity.telemetry.posthog` | PostHog 저장소와 전송기(기본 `UnityWebRequest`) | telemetry |
| `com.bun3.unity.telemetry.sentry` | Sentry 저장소, 오류 보고에 로컬 로그 꼬리 첨부, 동의 래치, 첨부 빈도 제한, SDK 옵션 구성 | telemetry, Sentry Unity SDK |

- UI 패키지가 텔레메트리를 모르게 한다. 그래서 팝업 연동은 텔레메트리 패키지 안의 선택 어셈블리로 둔다(§7-2).
- 원격 저장소는 저장소마다 별도 패키지다(결정 10). 게임은 쓰는 저장소의 패키지만 설치한다. Sentry는 SDK 의존성 때문에도 분리가 필요하다.

### 4.2 기록 형식

- 기록 하나는 이름, 분류, UTC 시각, 실행 안 순번, 공통 속성, 이벤트 속성(키·값 목록)이다.
- 분류와 단계는 JP 구성을 그대로 가져온다.
  - 분류: `Analytics`, `Ui`, `Popup`, `Scene`, `Interaction`, `EngineLog`, `Activity`
  - 단계: `Analytics`(분석), `Debug`(UI·팝업·씬·상호작용·엔진 로그), `Activity`(잦은 행동)
  - 저장소는 받을 단계의 조합을 가진다.
- 공통 속성
  - 고정: `distinct_id`(게임이 넣는 플레이어 ID), `run_id`, `build`, `environment`, `scene`, `language`
  - 게임 추가: 게임이 기록 시점마다 채우는 키·값 목록. JP는 `lobby_id`, `match_id`, `is_host`, `session_seconds`, `role`, `room`을 넣는다.
  - 공통 속성은 허브가 기록 시점에 게임의 공급 함수를 불러 채운다. 공급 함수가 예외를 던져도 기록은 남긴다.

### 4.3 허브와 조립

- 게임은 시작 코드에서 빌더로 허브를 만든다. 넘기는 것은 다음과 같다.
  - 공통 속성 공급 함수
  - 수집 동의 여부 함수. 원격 저장소만 이 값을 따른다.
  - 지금 환경의 옵션 묶음(§4.4)
  - 기록에서 뺄 속성 키 목록(§4.6)
- 저장소는 게임이 빌더에 한 줄씩 붙인다(앞선 결정). 원격·콘솔 저장소가 받을 단계와 접속 값은 환경 옵션 묶음에서 읽는다. 받을 단계가 비었거나 키가 없으면 그 저장소는 붙지 않는다.
- 저장소 하나가 예외를 던져도 다른 저장소와 게임은 계속 동작한다.
- 진입점은 `Telemetry.Track(분류, 이름, 속성…)`이다. 허브가 없으면 모든 호출을 무시한다.
- **시작과 수명은 kit이 맡는다(§7-8).** 게임은 빌더를 구성한 뒤 설치 호출 한 번만 한다. 그러면 kit이 다음을 한다.
  - 허브를 진입점에 연결한다.
  - 자동 기록(UI 조작·씬 전환·엔진 로그)을 설치한다. 게임이 `PopupStack`을 넘기면 팝업 기록도 설치한다. 자동 기록에는 켜고 끄는 옵션이 없다(앞선 결정).
  - 장면 전환에 살아남는 실행기 오브젝트를 만들어 저장소의 주기 처리(`Tick`)를 돌린다.
  - 종료 시(`Application.quitting`) 제한 시간 안에서 저장소를 비운다.
  - 게임의 매 프레임 처리는 kit 실행기에 끼우지 않는다. JP의 방 위치 추적과 미션 팝업 판정은 JP가 자기 실행기로 돌린다.
- **동의 함수 계약:** 허브는 기록마다 동의 함수를 불러 원격 저장소(PostHog·Sentry)에 보낼지 정한다. 로컬 JSONL·콘솔·기록 보관은 동의와 무관하게 받는다(JP 현재 동작). 게임은 동의가 바뀌면 kit에 알린다. Sentry의 "한 번이라도 꺼졌으면 첨부 안 함" 래치가 이 알림으로 동작한다.

### 4.4 환경 옵션 (결정 7)

- 환경의 종류와 판정은 게임이 정한다. kit에는 환경 열거형이나 판정 코드가 없다.
- kit은 환경에 따라 바뀌는 값을 한 묶음의 옵션 타입으로 노출한다(결정 11).
  - 묶음은 환경 이름과 저장소별 옵션 목록이다. 저장소 패키지마다 자기 옵션 타입을 하나씩 정의하고(코어의 콘솔, PostHog, Sentry), 묶음은 그 옵션들을 담는다. 나중에 저장소 패키지를 더하면 그 옵션 타입도 같은 묶음에 들어간다.
  - 게임 에셋에서 저장소 옵션을 골라 넣을 수 있게 다형 직렬화(`SerializeReference`)로 담는다. `com.bun3.unity.core`가 이미 쓰는 방식(`serializereference-extensions` 의존)이다.
  - 저장소는 빌더에 붙을 때 묶음에서 자기 옵션을 찾는다. 옵션이 없거나 받을 단계가 비었거나 키가 없으면 붙지 않는다. 이 타입은 kit이 에셋으로 내놓지 않는 일반 직렬화 클래스다. 게임이 자기 설정 에셋에 환경별로 저작하거나 코드로 만든다(§7-9). JP는 지금의 `TelemetryConfig` 에셋에 네 환경의 묶음을 둔다.
  - 환경 이름: 모든 기록의 `environment`와 Sentry environment 태그
  - 콘솔 옵션(코어): 받을 단계
  - PostHog 옵션: 호스트, 키, 받을 단계
  - Sentry 옵션: DSN, 받을 단계, SDK 디버그 출력 여부
- 게임은 시작할 때 지금 환경의 묶음을 하나 골라 넘긴다.
- JP의 묶음은 지금 동작을 옮긴 값이다.
  - `editor`: 콘솔 전부, PostHog·Sentry 없음, Sentry 디버그 출력 켬
  - `dev`·`playtest`: PostHog 전부, Sentry 분석+디버그
  - `release`: PostHog 분석만, Sentry 분석+디버그
  - 판정은 JP가 그대로 한다. 에디터 여부, Development Build, `JP_RELEASE` 정의를 본다.
- 키와 DSN을 묶음에 넣었으므로 환경마다 다른 PostHog 프로젝트로 보낼 수 있다(§7-3).

### 4.5 저장소

- **로컬 JSONL:** 실행마다 파일 하나를 쓴다. 보관 실행 수와 파일 최대 크기를 받고, 쓰기는 잠금으로 보호한다. 파일 끝부분을 읽는 기능(`ReadTail`)은 Sentry 첨부에 쓴다.
- **콘솔:** 한 줄 JSON을 Unity 콘솔에 찍는다.
- **PostHog(별도 패키지):** 묶음 크기·전송 주기·대기열 상한을 받는다. 전송은 교체 가능한 전송기(기본 `UnityWebRequest`)로 한다. 401이나 할당량 초과를 받으면 그 실행 동안 전송을 멈춘다. 엔진 로그(`EngineLog` 분류)는 받을 단계와 상관없이 보내지 않는다(결정 13).
- **기록 보관(JP의 `MatchHistorySink`를 일반화, 결정 12):** "판"을 모르는 메모리 보관함이다. 무엇을 받을지는 다른 저장소처럼 붙일 때의 단계로 정한다.
  - 게임이 `Open()`을 부르면 비우고 받기 시작한다. `Close()`를 부르면 비우고 받기를 멈춘다. 처음에는 닫혀 있고, 닫혀 있는 동안 들어온 기록은 버린다. 두 호출은 몇 번 불러도 안전하다.
  - 용량을 넘으면 `Debug` 단계 기록부터 버린다. 이벤트 이름으로 골라 읽는 API(`Find(names)`)가 있다. JP의 `match_ended` 요약과 행동기록 오버레이가 이 API를 쓰고, 논의 중인 결과 화면 기록도 쓸 수 있다.
  - JP는 매치 진입(`MatchTelemetry.Entered`)에서 열고, 활성 씬이 `Menu`로 바뀔 때 닫는다. 결과 후 방 유지 복귀, 준비 시간 초과로 무산된 판의 복귀, 연결 끊김·나가기가 모두 `Menu` 전환을 지난다. 나가기 경로는 `match_ended`를 쓴 뒤에 `Menu`를 불러와서 요약이 비지 않는다. `MatchState`가 사라질 때 닫지 않는 이유는 연결이 끊기면 NGO가 먼저 꺼진 뒤 나가기 경로가 보관함을 읽기 때문이다.
- **Sentry(별도 패키지):** 받은 기록을 브레드크럼으로 넣는다. 게임이 지정한 공통 속성 키를 태그로 단다(JP는 `lobby_id`, `match_id`).
  - 오류 보고에는 로컬 JSONL 꼬리(최대 1 MiB)를 붙인다. 같은 실행 안에서 첨부는 60초에 한 번이다.
  - 실행 중 동의가 한 번이라도 꺼졌으면 그 실행 동안 첨부하지 않는다.
  - JP의 첨부 가리기(`JoinCodeMask`)는 결정 4로 빠진다.
  - **SDK 초기화(§7-10):** Sentry Unity SDK는 프로젝트의 `SentryOptions` 에셋이 가리키는 옵션 구성 스크립트(`SentryOptionsConfiguration`)로 초기화된다. kit은 이 구성의 추상 기반 클래스를 제공한다. DSN·environment·디버그 출력은 환경 묶음에서, 첨부·동의 래치·빈도 제한은 kit이 채운다. 게임은 이 클래스를 상속해 지금 환경의 묶음과 동의 값을 돌려주는 두 지점만 구현하고, 그 에셋을 `SentryOptions`에 연결한다. JP의 `JpSentryOptions`가 이 상속 클래스가 된다.
  - 이 패키지는 SDK를 필수 의존성으로 둔다. Sentry가 필요 없는 게임은 이 패키지를 설치하지 않는다. 패키지 테스트는 SDK 호출을 감싼 인터페이스(JP `ISentryApi`)의 가짜로 돈다.

### 4.6 개인정보 (결정 4·5)

- 허브는 게임이 넘긴 키 목록에 든 속성을 기록에서 빼고 경고를 남긴다. JP는 채팅 본문과 인증 토큰의 키를 넘긴다.
- 그 밖의 값은 가리지 않는다. SteamID, 닉네임, 참가 코드, 엔진 로그 원문이 해당한다.
- UI 자동 기록은 입력칸 내용을 어떤 경우에도 담지 않는다. 어느 입력칸인지(경로)와 글자 수만 남긴다. 이 규칙은 kit의 규칙이라 게임 설정으로 바꿀 수 없다.

### 4.7 자동 기록

- **UI 조작:** 버튼·토글·슬라이더·드롭다운·입력칸 제출을 기록한다. 같은 컨트롤을 1초 안에 연달아 누르면 첫 클릭은 바로 남기고, 연타가 끝나면 횟수를 요약 한 건으로 남긴다(JP `ClickBurst`). 컨트롤은 루트부터의 계층 경로로 가리킨다. `(Clone)`을 떼고 드롭다운 항목의 옵션 문구는 남기지 않는다.
- **씬 전환:** 활성 씬이 바뀔 때 `from`·`to`를 남긴다.
- **엔진 로그:** 경고 이상을 남긴다. 게임이 지정한 접두어의 로그 줄은 등급과 상관없이 남긴다(JP는 `[JP.Net]`).
- **팝업(연동 어셈블리):** 게임이 넘긴 `PopupStack`의 열림·닫힘과 열려 있던 시간을 남긴다. 구독 함수의 예외는 팝업 열기·닫기 흐름으로 새지 않는다.
  - JP는 지금 `GamePopups`가 kit 스택 이벤트를 받아 다시 내보낸다. 전환 뒤에는 kit 팝업 기록이 스택을 직접 듣는다.
  - JP의 미션 팝업 중단 판정은 JP가 같은 스택 이벤트를 직접 들어 처리한다.

### 4.8 JP 전환 (결정 9)

- JP는 `✨/analytics-log-system` 브랜치에서 kit 패키지를 참조한다. 개발 중에는 kit 브랜치 `Bun3/jp-telemetry`를 패키지 주소에 지정한다. 기존 `#Bun3/jp-chat` 예외와 같은 방식이고, JP `unity/CLAUDE.md`의 승인 예외 목록에 추가한다.
- 개발 중에는 JP manifest가 kit 작업 공간을 임시 `file:` 경로로 참조한다. JP를 `main`에 넣기 전에 kit 브랜치를 원격에 올리고 브랜치 주소로 바꾼다. 원격에 올리는 시점은 그때 사용자 확인을 받는다.
- 파일별 행선지
  - kit 코어: `Telemetry`, `TelemetryHub`, `TelemetryTypes`, `TelemetryJson`, `LocalJsonlSink`, `ConsoleSink`, `PostHogSink`, `MatchHistorySink`·`MatchHistory`(일반화), `EngineLogCapture`, `UiControlTracker`, `UiInteractionCapture`, `UiPath`, `ClickBurst`, `DebugCaptures`의 `SceneCapture`, `TelemetryRunner`의 저장소 주기 처리
  - kit 팝업 연동: `DebugCaptures`의 `PopupCapture`
  - kit Sentry: `SentrySink`, `ISentryApi`, `SentrySettings`, `JpSentryOptions`의 공통부·`SentryPrivacy`
  - 없앰: `JoinCodeMask`, `TelemetryEnvironments`의 kit 쪽 역할(JP가 환경 판정만 남긴다)
- 옮긴 파일은 JP에서 지운다. JP에 남는 것은 다음과 같다.
  - 이벤트 정의: 아웃게임 14개, 인게임 10개
  - 공통 속성 공급 함수(`TelemetryContextSource`)
  - JP 환경 판정과 환경별 옵션 묶음
  - 시작 조립 코드
  - 행동 알림(`ActivityLedger`·`ActivityNotice`·`ActivityRecorder`)
  - 기록 보관 열기·닫기 호출(매치 진입, `Menu` 씬 전환)
  - 미션 단계 키, 방 위치 추적, 설정 변화 기록(`TelemetryDiffs`), 로비 머문 시간 요약, 넷 로그 변환(`NetLogLine`), 미션 팝업 중단 판정, 플레이어 번호, 방 위치 추적·미션 팝업 판정을 돌리는 JP 실행기
- 결정 4에 따라 JP의 참가 코드 가리기, 닉네임·입력 텍스트·참가 코드 키 차단을 없앤다.
  - JP 설계 문서(`docs/superpowers/specs/2026-10-28-analytics-debug-logging-design.md`, `2026-11-01-in-game-activity-logging-design.md`)와 `docs/playtest-guide.md`의 개인정보 규칙도 같은 작업에서 고친다.
  - JP 소스 검사 테스트(`TelemetryPrivacyScanTests`)도 새 규칙에 맞춘다.
- JP 테스트에서 kit으로 옮긴 코드의 테스트는 kit 패키지 테스트로 옮긴다. JP 전체 테스트는 전환 전 기준선 실행과 비교해 새로 실패하는 테스트 이름이 없어야 한다. 전체 실행의 연쇄 실패처럼 기존에 알려진 불안정은 해당 클래스를 따로 다시 돌려 가린다.

## 5. 제약

- bun3-kit 규칙을 따른다.
  - 코드·XML 문서·패키지 메타데이터는 영어만 쓴다. 모든 public 멤버에 XML 문서를 단다.
  - 빌드 경고 0. Unity 계층 문자열은 ZString을 쓰고, 매 프레임 경로에서 할당하지 않는다.
  - 폴더는 네임스페이스를 따른다. 내용이 바뀌면 버전을 올린다.
- 패키지 최소 Unity 버전은 kit의 다른 Unity 패키지와 같은 `6000.3`이다. JP는 6000.5.5f1이다.
- 새 외부 의존성은 ZString과 Sentry Unity SDK다. JP는 이미 둘 다 쓰고 있다. JP의 `docs/third-party/` 고지는 바뀌지 않는다.
- kit 저장소의 Unity 개발 프로젝트(`unity/Packages/manifest.json`)에 ZString과 Sentry SDK를 git 주소로 추가한다. 패키지 `package.json`도 UniTask처럼 git 주소 의존성으로 적는다.

## 6. 테스트

- 순수 로직은 패키지 EditMode 테스트로 검증한다. 허브 분배, 단계 거르기, 속성 키 제외, 공통 속성 공급 예외, JSON 줄 형식, 로컬 파일 회전·꼬리 읽기, PostHog 묶음·중단 상태, 기록 보관 열기·닫기·용량·`Find`, 환경 옵션에 따른 저장소 조립, Sentry 첨부 래치·빈도 제한이 대상이다. JP에 있는 같은 테스트를 옮겨 출발점으로 쓴다.
- UI 조작, 팝업 스택 연동, 씬 전환처럼 실제 Unity 객체가 필요한 것은 패키지 PlayMode 테스트로 검증한다.
- 입력칸 내용이 어떤 기록에도 들어가지 않음을 테스트로 고정한다.
- JP는 전환 뒤 EditMode·PlayMode 전체를 돌려 기준선과 비교한다.

11. **개발 중 JP는 kit 작업 공간을 임시 `file:` 경로로 참조한다.** 브랜치를 원격에 올리기 전에도 JP에서 테스트하려는 것이다. 이전 효과음 키 작업에서도 같은 방식을 썼다. 틀리면 kit 브랜치를 먼저 원격에 올린다.
