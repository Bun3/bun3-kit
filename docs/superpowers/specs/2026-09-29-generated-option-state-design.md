# 생성 상태와 중첩 옵션 변경 기록 — 첫 구현 설계

## 상태와 목적

2026-09-29 대화에서 사용자는 자체 C# 생성기, 중첩 옵션과 추적 컬렉션, 변경 단위 롤백, 기존 저장 형식과의 변환을 첫 검증 대상으로 삼는 방향에 동의했다. **2026-09-30 승인된 구현, 패키지·측정 검증, 전체 브랜치 리뷰와 지적 사항 수정·재리뷰를 완료했다.** 현재 구현·측정은 [사용 가이드](../../generated-option-state.md)와 SDD 작업 보고서에 기록한다. 패키지 배포와 기존 게임 이전은 수행하지 않았다.

목표는 게임 코드에서 `item.State.Option.RerollOptions[0].Level = 5`처럼 수정하면 프레임워크가 이전 값 기록과 아이템 Dirty 전파를 맡는 것이다. 트랜잭션 없이도 같은 상태와 인벤토리를 사용할 수 있어야 한다. 롤백은 기존 객체와 목록의 내용을 제자리에서 복원한다.

설계 근거는 [세 게임의 상태·저장 조사](../../research/2026-09-29-game-state-generation-and-persistence.md)와 [변경 기록 방식 조사](../../research/2026-09-29-property-change-rollback.md)다. 구현 후 현재 계약은 [롤백 가이드](../../outgame-rollback.md)와 [생성 상태 사용 가이드](../../generated-option-state.md)에 함께 기록되어 있다.

기존 미커밋 수정은 보존한다. 이 문장을 처음 작성한 설계 단계에서는 제품 코드와 패키지 버전을 변경하지 않았다. 이후 승인된 구현에서 `Bun3.State` 0.1.0과 Items 0.5.0을 준비했다. 외부 게임, DB, 커밋·배포 상태는 변경하지 않았다.

## 1. 이번 구현의 범위

포함한다:

- private 필드에서 추적 프로퍼티와 직접 복원 코드를 생성하는 C# 생성기.
- 중첩 상태, `TrackedList<T>`, 소유권 검증, 변경 단위 Undo 기록.
- `ItemInventory<TState>`의 로딩·생성·상태 교체·삭제·이동과 자동 연결.
- 기존 `Transaction` 안에서 옵션, 재료 수량, 업적 상태를 함께 되돌리는 통합 검증.
- 기존 형식에 대응하는 JSON/protobuf fixture와 명시적 매핑의 왕복 검증.
- 비활성·활성 트랜잭션의 할당 및 변경량에 따른 보관 비용 측정.

이번에는 포함하지 않는다:

- 실제 세 게임의 코드/DB 이전, NMF 도입, Unity/IL2CPP 지원 완료 주장.
- 임의 protobuf 객체의 setter 가로채기, 범용 ORM·protobuf 매핑 자동 생성.
- 영속 Undo/Redo 이력, 중첩 트랜잭션, 동시 쓰기, 프로세스 장애 복구.
- 인벤토리의 멤버십·재생 기준 사전 전체를 변경 로그로 교체하는 작업.
- 공통 DB 저장 큐·재시도 모듈의 전면 신설. 해당 모듈은 별도 설계 대상으로 남긴다.

**무복사 보장은 생성 상태의 롤백에 적용된다.** 현재 `ItemInventory.Transaction.cs`는 최초 참여 때 인스턴스 사전과 재생 기준 사전을 얕게 복사한다. 이 보관은 이번 단계에 남는다. 따라서 옵션 깊은 복사가 없어져도 전체 인벤토리 트랜잭션이 변경량에만 비례한다고 표현하면 안 된다.

## 2. 구조와 책임

| 위치 | 책임 |
|---|---|
| `common/src/Bun3.State/` | 추적 attribute·interface, 상태 소유권, 추적 목록, 타입별 변경 기록과 역순 복원 |
| `common/src/Bun3.State.Generator/` | private 필드 분석, 프로퍼티·복원·자식 연결 코드와 진단 생성 |
| `server/src/Bun3.Server.Items/` | 생성 상태를 인스턴스의 Dirty 및 기존 Transaction 참여에 연결 |
| `server/src/Bun3.Server.Core/` | 기존 플레이어별 Transaction과 모든 참여자의 확정 후 알림 계약 유지 |
| 게임 코드 | 상태 필드·기본값·게임 규칙, DB 컬럼·JSON·protobuf 매핑 |

공용 런타임은 서버 패키지, DB, protobuf를 참조하지 않는다. 생성기는 빌드 도구다. 런타임은 netstandard2.1/C# 9, 생성기는 기존 저장소의 analyzer처럼 컴파일러 호스트용 netstandard2.0/C# 9로 구성한다. 생성 결과는 C# 9에서 컴파일되어야 한다.

생성기는 상태 partial class에 추적 interface와 내부 메타데이터를 추가한다. 새로운 기반 클래스 상속을 강제하지 않는다. 공용 interface를 명시적으로 구현해 일반 게임 코드에 프레임워크 조정 메서드가 불필요하게 노출되지 않도록 한다.

생성기 DLL은 런타임 패키지의 analyzer 자산으로 제공한다. Roslyn은 게임 런타임 의존성에 포함하지 않는다. 새 런타임 패키지는 최초 구현 시 `0.1.0`, Items는 새 공개 기능에 맞춰 `0.5.0`으로 올린다. 다른 패키지 소스까지 변경하면 해당 버전도 올린다.

## 3. 게임이 작성하는 스키마

아래 이름과 사용 모양을 첫 구현의 기준으로 삼았다. 현재 구현의 API와 사용 예는 [사용 가이드](../../generated-option-state.md)를 따른다.

```csharp
[TrackedState]
public sealed partial class EquipmentState
{
    [Tracked]
    private int _level = 1;

    [Tracked]
    private EquipmentOptionState _option = new EquipmentOptionState();
}

[TrackedState]
public sealed partial class EquipmentOptionState
{
    [Tracked]
    private readonly TrackedList<RerollOptionState> _rerollOptions =
        new TrackedList<RerollOptionState>();
}

[TrackedState]
public sealed partial class RerollOptionState
{
    [Tracked]
    private int _id;

    [Tracked]
    private int _level;
}
```

생성 프로퍼티 이름은 private 필드의 선행 `_`를 제거하고 첫 글자를 대문자로 만든다. 스칼라와 자식 상태에는 getter/setter, readonly 추적 목록에는 getter를 생성한다. 이름이 충돌하면 빌드 오류로 진단한다.

첫 버전은 namespace 아래의 비제네릭 sealed partial class를 지원한다. 중첩 class 선언, 추적 상태끼리의 상속, generic 상태, struct 상태는 명확한 진단으로 거부한다. 추적과 무관한 기존 기반 클래스는 허용한다. 이 제한은 객체 그래프의 중첩과 다르며, 옵션이 옵션을 소유하는 것은 지원한다.

추적 가능한 값은 C# 기본 값 타입, enum, string, decimal, DateTime, DateTimeOffset, TimeSpan, Guid와 그 nullable 값, 생성 상태, 해당 값/상태를 담는 `TrackedList<T>`다. 임의 가변 class, 배열, `List<T>`, `Dictionary<TKey,TValue>`, protobuf 메시지는 추적 필드로 허용하지 않는다. 사용자 정의 struct도 첫 버전에서는 거부해 내부 가변 참조를 놓치지 않는다.

private 필드는 초기값 선언에만 직접 쓰고, 이후에는 생성된 프로퍼티를 사용한다. 사용자 코드의 직접 대입·증감·ref/out 노출은 analyzer 오류로 막는다. 생성 코드 자신의 초기화·복원은 이 진단에서 제외한다. 생성 대상 스키마에 선언한 가변 인스턴스 필드의 누락도 진단한다. 상속받은 상태·reflection·unsafe 변경까지 자동 추적한다고 보장하지 않는다.

## 4. 변경과 소유권

### 일반 변경

setter는 동일 값 대입을 먼저 걸러낸다. 스칼라는 값 비교, 자식 상태는 참조 비교를 사용한다. 변경이 있으면 다음 순서를 따른다.

1. 새 자식의 소유권과 타입 등 실패 가능한 조건을 검증한다.
2. 트랜잭션이 활성일 때 이전 값과 필요한 소유권 정보를 기록한다.
3. 값을 적용하고 자식의 연결 상태를 갱신한다.
4. 현재 연결된 루트 아이템을 Changed로 표시하고 인벤토리 Dirty 경로를 호출한다.

검증 오류는 상태·소유권·Dirty를 바꾸지 않는다. 사용자 콜백 실패는 기존 알림 정책을 따른다. 메모리 부족 등 복구 불가능한 실패까지 강한 예외 안전성을 약속하지 않는다.

### 트리 소유권

이 절의 루트 소속은 소유 아이템을 기준으로 한다. `item.State` 객체를 교체해도 해당 아이템의 기록 소속 식별자는 바뀌지 않는다. 연결 전 상태 트리에서는 객체 간 단일 부모 관계만 관리하고, 아이템 연결 시 전체 트리의 소유권을 검증한다.

한 가변 노드는 한 위치에만 연결된다. 같은 노드를 다른 아이템, 두 프로퍼티 또는 목록의 두 위치에 동시에 넣을 수 없다. 자기 자신이나 조상을 자식으로 넣는 순환도 거부한다. 실패는 기존 구조를 변경하기 전에 판정한다. 불변 스칼라/string 공유는 허용한다.

일반적인 제거는 연결을 해제한다. 활성 트랜잭션에서 제거·교체한 노드는 **연결 위치는 없어져도 복구를 위한 기록 소속은 유지**한다. 외부에 보관한 그 노드를 수정해도 같은 Undo 기록에 들어간다. 연결된 아이템이 없으므로 해당 수정만으로 현재 아이템을 다시 Dirty 처리하지는 않는다.

기록 소속을 유지한 노드는 같은 트랜잭션 안에서 원래 루트의 다른 위치로 다시 연결할 수 있다. 다른 루트로의 연결은 해당 트랜잭션이 끝날 때까지 거부한다. commit 뒤 최종적으로 분리된 노드는 기록 소속을 해제한다. rollback은 원래 위치와 소유권을 복원한다.

새로 추가한 노드도 같은 규칙을 따른다. 추가 후 수정하다 rollback하면 목록에서 제거되고, 추가 시점 이후 추적된 필드 변경도 복원된다. 복구에 필요한 참조만 유지하고 완료 후 해제한다.

### 추적 목록

`TrackedList<T>`는 읽기, 순회, Add, Insert, Remove, RemoveAt, 인덱스 교체, Clear를 제공한다. 내부 가변 `List<T>`나 배열을 노출하지 않는다. 잘못된 인덱스나 소유권 위반은 기록 전에 거부하고, 없는 값의 Remove와 빈 Clear는 변경으로 기록하지 않는다.

첫 구현에서 Clear는 각 원소 제거를 기록해 전체 Undo 순서에 통합한다. 삭제한 원소 참조와 위치를 보관해야 하므로 Clear 비용은 삭제한 원소 수에 비례한다. 제거한 모든 값을 아무 정보 없이 복원하는 것을 목표로 삼지 않는다.

## 5. 기록과 복원

| 동작 | Undo 보관 내용 | 역순 복원 |
|---|---|---|
| 스칼라 변경 | 대상, 필드 식별자, 타입 그대로의 이전 값 | private 필드에 직접 대입 |
| 자식 교체 | 이전 자식 참조, 연결 관계 | 이전 참조와 소유권 복원 |
| 목록 추가 | 목록, 추가 위치 | 해당 위치 제거 |
| 목록 삭제 | 목록, 삭제 위치, 삭제한 값/참조 | 같은 위치에 삽입 |
| 목록 원소 교체 | 목록, 위치, 이전 값/참조 | 이전 원소 복원 |

첫 버전은 **모든 실변경을 순서대로 기록**한다. 최초 필드 변경만 보관하는 중복 제거는 적용하지 않는다. 목록에서 제거한 객체의 후속 변경과 재삽입이 섞여도 전체 순서의 역전이 정확해야 하기 때문이다.

스칼라 이전 값을 object로 boxing하거나, 매 변경마다 Action/클로저·이벤트 객체·문자열을 생성하지 않는다. 타입별 재사용 버퍼와 전체 순서 인덱스를 사용한다. 용량 증가는 허용하되 정해진 작업량으로 준비된 이후의 변경 경로를 할당 측정으로 검증한다.

복원은 생성된 내부 복원 코드와 목록 내부 연산으로 수행한다. 공개 setter, 게임 로직, 외부 콜백을 호출하지 않는다. 모든 상태 기록을 역순으로 되돌리고, 기존 인스턴스/인벤토리 변경 표시를 시작 시점으로 복원한다. 시작 전에 이미 Dirty였던 아이템을 깨끗하게 만들면 안 된다.

commit은 상태를 유지하면서 Undo의 참조를 해제한다. 저장 대기 변경은 유지한다. 용량은 재사용하되 완료된 트랜잭션의 객체를 버퍼가 붙잡지 않아야 한다.

## 6. 기존 인벤토리와의 연결

인벤토리가 생성 상태 루트를 식별하면 자동으로 추적 소유자를 연결한다. 사용자가 아이템마다 이벤트를 구독하거나 transaction을 자식마다 전달하지 않는다. 인벤토리 없는 상태 객체도 생성·읽기·수정할 수 있으며, 연결되기 전에는 인벤토리 Dirty나 서버 Transaction에 영향을 주지 않는다.

생성 상태의 Undo 버퍼는 인벤토리의 기존 `ITransactionParticipant` 수명에 포함한다. 옵션만 바뀌어도 해당 아이템의 기존 Changed 상태를 먼저 보관하고 인벤토리를 참여시킨다. 별도 참여자의 우연한 enlist 순서에 상태 복원과 소유권 복원을 의존시키지 않는다.

| 경로 | 계약 |
|---|---|
| `TryLoadInstance` | 완성된 상태 트리를 연결하되 Dirty·Undo·알림을 만들지 않음. 활성 트랜잭션에서는 기존처럼 거부 |
| 아이템 생성 | 새 루트 연결. 실패/rollback 시 생성한 아이템과 상태 소유자 분리 |
| 생성 상태 내부 변경 | `snapshotState`나 `BeginStateChange()` 없이 자동 추적 |
| `item.State = replacement` | 새 루트를 검증하고 이전 루트를 기록. rollback 시 이전 루트 참조와 자식 내용 복원 |
| 아이템 삭제 | 활성 트랜잭션이면 상태의 기록 소속을 유지. commit 때 최종 분리, rollback 때 소유권 복원 |
| 인벤토리 간 이동 | 기존처럼 활성 트랜잭션에서는 거부. 정상 이동은 상태의 소유자를 새 인벤토리로 연결 |
| `DrainChanges` | 기존처럼 활성 트랜잭션에서 거부. 기존 버퍼 소유권 계약 유지 |

상태 교체와 자식 변경의 기록은 같은 인벤토리 Undo 순서에 통합한다. 복원 도중 공개 State setter를 호출하지 않는다. 모든 데이터와 연결 관계를 복원한 뒤 외부 알림 없이 시작 시점의 변경 표시를 되살린다.

기존 opaque `TState`는 기존 스냅샷 계약을 유지한다. 동일 인스턴스에 생성 상태 추적과 깊은 복사 scope를 혼합하지 않는다. 생성 상태에 `BeginStateChange()`를 호출하면 편집 시작 전에 명확한 예외로 거부한다. 기존 호출자의 동작이 바뀌는 것은 새 생성 상태를 선택한 경우뿐이다.

활성 트랜잭션이 없으면 Undo 보관 객체를 만들거나 Undo 항목을 쌓지 않고 일반 변경과 Dirty 알림만 수행한다. 빈 트랜잭션도 기록을 만들지 않는다. 여러 플레이어의 트랜잭션·소유권·버퍼는 독립적이다.

Core의 모든 참여자 내부 확정 → 외부 알림 순서는 유지한다. commit 알림의 예외가 확정한 데이터를 롤백하거나 다른 참여자의 정리를 생략하게 해서는 안 된다. 업적은 기존 구현을 이용하며 생성 상태로 이전하지 않는다.

## 7. 저장 형식과 변환

```text
DB JSON/blob → protobuf DTO → 연결 전 생성 상태 → 인벤토리에 연결
                                                  ↓ 게임에서 수정
DB JSON/blob ← protobuf DTO ← 저장 시 명시적 매핑 ← 생성 상태
```

게임별 매핑 함수는 DTO를 생성 상태로 구성하고 반대 방향으로 변환한다. protobuf 생성 코드를 수정하지 않는다. 로딩 중 상태는 아직 인벤토리에 연결되지 않았으므로 값을 채우는 과정이 저장할 새 변경으로 취급되지 않는다.

첫 fixture는 idlez 계열의 JSON/Google.Protobuf 및 growninja·growdaemon 계열의 protobuf-net blob에서 관찰한 중첩 상태·목록·필드 존재 여부를 대표한다. 실제 게임 이름은 제품 소스와 fixture 이름에 쓰지 않는다. fixture 스키마와 고정 payload의 대응 관계는 연구/검증 문서에 기록한다.

기존 필드 번호, 목록 순서, 명시적 0과 미설정 값의 구분, null/빈 메시지 구분을 보존한다. nullable 추적 필드로 presence를 표현하고 매핑 때 이를 적용한다. 프로토콜에 따라 표현 불가능한 구분을 새로 만들어 약속하지 않는다.

알 수 없는 필드를 보존하려면 로딩한 DTO의 복제본을 게임 매핑이 소유하는 저장 메타데이터로 보관하고, 저장 시 복제본의 알려진 필드만 갱신한다. 자식 DTO의 메타데이터는 원소 위치가 아니라 해당 상태 객체와 연결해 순서 변경에도 보존한다. 이 DTO는 게임 로직에 가변 상태로 노출하지 않으며, 게임 필드의 기준 데이터로 사용하지 않는다. 이 비용은 로딩/저장 경로의 호환성 비용이고 Undo 스냅샷이 아니다.

저장 메타데이터는 생성 상태의 추적 필드 밖에서 매핑 모듈이 관리한다. 제거된 상태 객체를 메타데이터 테이블이 영구적으로 붙잡지 않도록 객체 수명에 연동한다. 새로 만든 상태에는 보존할 이전 DTO가 없으므로 새 DTO를 만든다.

JSON에서는 로딩한 JSON 객체의 알려지지 않은 속성을 보존하는 병합 매핑을 별도로 검증한다. protobuf JSON 변환만으로 알 수 없는 속성이 유지된다고 가정하지 않는다. 저장 형식별 보존 가능 범위를 fixture가 명시해야 한다.

JSON/blob 직렬화와 SQL은 게임 매핑에서 수행한다. DB에는 옵션 컬럼 전체를 다시 쓸 수 있다. 메모리의 변경 단위 롤백과 DB 부분 UPDATE를 같은 기능으로 취급하지 않는다.

### 저장 확정과 Dirty

Undo 수명은 게임 동작 단위다. 저장 대기 목록 수명은 DB 성공 확인까지다. 메모리 commit으로 저장 대기 변경을 지우지 않는다.

첫 구현은 기존 `DrainChanges`와 `Player` 저장 버전 계약을 사용한다. `DrainChanges`는 DB ACK가 아니며, 저장 작업은 전달받은 버퍼를 성공까지 보유한다. 저장 중 상태를 다른 스레드에서 읽으며 직렬화하지 않는다. 직렬화할 DTO/payload와 저장 버전은 세션 실행 안에서 준비하고, 외부 I/O에는 그 결과를 전달한다.

저장 실패 시 같은 저장분을 유지하고, 성공 시 그 저장분만 해제한다. 저장 중 생긴 새 변경은 다음 저장 대상으로 남는다. 이 첫 단계에서는 옵션만의 별도 ACK API나 `OptionDirty` 최적화를 추가하지 않고, 아이템이 Updated면 옵션을 다시 직렬화한다. 옵션 전용 저장 최적화와 공통 저장 큐는 후속 설계에서 다룬다.

## 8. 검증 기준

테스트는 생성된 실제 프로퍼티와 공개 목록/인벤토리 동작으로 수행한다. 생성 문자열 전체 비교나 private 버퍼 필드명 검사는 주 검증으로 삼지 않는다.

| 영역 | 필수 시나리오 |
|---|---|
| 생성 | C# 9 컴파일, 이름 충돌/지원하지 않는 필드/직접 쓰기 진단, 기존 기반 클래스와 공존 |
| 선택적 사용 | transaction 없음, 비활성, 빈 transaction, 동일 값 대입; Undo 기록/보관 미생성 |
| 스칼라 | 여러 번 수정, 원래 값으로 재변경, nullable 및 enum 복원 |
| 중첩 옵션 | 자식과 손자 변경, 목록 원소 내부 변경, root 교체 전후 변경 |
| 목록 | Add/Insert/Remove/RemoveAt/인덱스 교체/Clear 혼합 뒤 값·순서·객체 참조 복원 |
| 분리된 노드 | 제거 → 외부 참조로 수정 → 재삽입 → rollback; commit 후 분리 노드가 이전 아이템을 Dirty 처리하지 않음 |
| 소유권 | 같은 노드 중복 연결, 타 아이템 공유, 순환 거부; 거부 전후 상태와 Dirty 동일 |
| 인벤토리 | 로딩, 새 아이템, 삭제, 상태 교체, 이동 뒤 소유자 변경; 기존 opaque 상태 회귀 유지 |
| 통합 롤백 | 재료 차감 → 옵션 변경 → 업적 진행 → 실패; 모두 원래 상태와 기존 Dirty로 복원 |
| commit | 외부 알림 전에 모든 참여자 확정, 콜백 실패 후에도 정리, commit 뒤 새 변경의 재진입 |
| 플레이어 격리 | 두 Transaction의 변경·완료가 서로 영향을 주지 않음 |
| 저장 왕복 | JSON/protobuf 고정 payload 로드·변경·저장·재로드, presence/unknown 데이터/목록 순서 검증 |
| 저장 실패 | 가짜 비동기 저장기의 실패 후 재시도, 저장 도중 새 변경이 과거 저장 ACK로 사라지지 않음 |
| 할당 | 준비된 버퍼로 scalar/child/list 변경을 반복해 비활성·활성 비용 측정, 작은 변경에서 옵션 크기에 비례한 복제 없음 |

필드 변경 도중 예외를 던지는 게임 콜백을 생성 setter에 두지 않는다. 검증기는 구조 검증과 게임 규칙 검증을 구별한다. 콘텐츠 규칙 실패는 게임이 Transaction을 commit하지 않는 경로로 검증한다.

검증 fixture에서 변환된 protobuf 값이 의미상 동일한지를 확인하고, 포맷이 보장하지 않는 정렬까지 포함한 byte 배열 완전 일치를 일반 계약으로 요구하지 않는다. 고정 wire payload는 필드 번호 및 presence 호환성 확인에 사용한다.

## 9. 완료 조건과 후속 판단

런타임/생성기 테스트, 서버의 관련 회귀 및 전체 테스트, Release 경고 없는 빌드가 통과해야 한다. analyzer를 포함한 로컬 패키지를 임시 소비 프로젝트에서 사용해 생성 코드가 빌드되는 것까지 확인한다. 실제 DB와 Unity 검증 여부는 별도로 보고한다.

결과 문서는 게임이 작성하는 필드 선언, 생성된 setter의 실제 예, 역순 복원 예, DTO 매핑 비용, 할당 측정 방법/결과를 담는다. 성능과 호환성은 실행한 검증 범위 안에서만 주장한다.

이 검증으로 옵션 추적과 변환의 사용성이 확인되면 다음 결정은 인벤토리 컨테이너 로그 전환과 공통 저장 조정 모듈이다. 이번 구현을 완료했다는 이유로 세 게임의 이전 또는 전체 스냅샷 제거까지 완료했다고 보고하지 않는다.
